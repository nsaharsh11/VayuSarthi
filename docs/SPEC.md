Authoritative domain rules:
- RUL and safety_buffer are flight cycles; each tail has cycles/day rate.
- RUL interval is [lower, upper], half-width = (upper-lower)/2.
- deadline_day = floor((RUL_point - safety_buffer) / rate), with no extra
  minus-one or today offset. Induction START must be on/before this day.
- Sort tails by (deadline_day, tail_id). For each, choose a spare, bay and
  crew and start at max(today+1, spare_available, bay_free, crew_free).
  Reserve bay and crew for duration days and consume the spare.
- Status is On time when start <= deadline, Late otherwise, Unplanned
  when no unused compatible spare is available within the horizon.
- Record the binding spare, bay or crew. Resource ties use spare/bay/crew
  priority; when tomorrow alone sets the start, record none.
- Decision float: perturb ONE tail's point by both signs in integer steps,
  rerun the entire planner, compare every (start,bay,spare,status). Smallest
  absolute change is the float; no change through R is reported as > R.
- Freeze placement for deadline slack in cycles:
  point - safety_buffer - rate*(start_day-today).
- Covered iff min(float,slack) >= half-width; otherwise Fragile. These
  describe planning attention only. A > R float establishes Covered only
  if R >= half-width and slack >= half-width; otherwise conservative Fragile.
  Unplanned tails have no finite placement slack and are Fragile.
- All fleet data and simulation output are fictional/simulated. NASA model
  metrics are benchmark results generated by scripts, never aircraft claims.
- Planner inputs have no ground truth. Randomness uses explicitly seeded
  numpy Generators; same inputs yield identical serialized outputs.

## 1. Project definition

**One-line pitch:** *A health prediction alone doesn't tell a maintenance team which plan stays workable when resources or estimates change. We integrate four data sources, then show where a maintenance plan flips, why, and what it would take to unblock it.*

**Problem framing (Air Power PS):** low aircraft availability from fragmented, reactive maintenance; health-monitoring, technical-record, spares, and maintenance-agency data not integrated.

**Abstraction (state this in the UI and README):** one engine module per **fictional civilian aircraft**. "Aircraft availability" = availability of that engine. Benchmark data (C-MAPSS) is replayed as if it were each tail's health feed. No combat tasking, no military parts-transfer optimisation.

### 3.4 Ground-truth firewall

`Scenario` has two parts: `truth` (failure cycle per tail, actual spare dates, actual agency calendar) and `beliefs` (what the planner is told). `PlanningState` (what planners/policies see) **has no truth fields**. Enforce with a test that statically scans `planner/` and `policies/` for imports of `scenario.truth` or the strings `failure_cycle` / `true_rul`.

### 3.5 Time and units

- Simulation time is integer **day** `0..H-1`. Raw CSV dates are ISO strings; the ingester converts with `day = (date - start_date).days`.
- One flying day for an operating tail consumes `cycles_per_day` cycles.
- **Cycle-to-day mapping (implement as one tested function):**
  `latest_start_offset(rul_cycles, cpd) = floor((rul_cycles - 1) / cpd)` if `rul_cycles >= 1` else `-1`.
  `deadline_day = today + latest_start_offset(...) - safety_buffer_days`.
  Rationale: starting maintenance on day `today+k` means the tail flew `k` days (`k*cpd` cycles); it is safe iff `k*cpd <= RUL-1`. An engine "fails" on completing the cycle that brings RUL to 0.

## Phase 2: RUL model and calibrated ranges (the only ML; keep it small and evaluated)

### 2.1 Features (causal only)
Per retained sensor, per engine, at cycle t using data from cycles ≤ t: last value, rolling mean/std/slope over each window in `window_sizes` (use expanding window when fewer cycles exist), plus `cycle` index. **Causality test:** truncating an engine's trajectory at cycle t must give identical features and prediction at t.

### 2.2 Training target
`min(true_rul, rul_cap)` (piecewise-linear cap, standard for C-MAPSS).

### 2.3 Grouped cross-validation (so fleets can use 100 distinct engine trajectories)
For each of `cv_folds` folds by engine id:
1. Held-out fold = evaluation engines.
2. From the remaining engines, hold out `calibration_engine_fraction` as calibration engines; train LightGBM on the rest.
3. Predict on calibration engines; compute residuals `e = true_rul - pred` (use rows with `true_rul <= rul_cap`), grouped by **predicted-RUL bin** (`predicted_rul_bins`).
4. For each bin store residual quantiles at 0.10, 0.50, 0.90.
5. For the held-out fold, produce `point = pred`, `low = max(0, pred + q10[bin])`, `high = pred + q90[bin]`; enforce `low <= point <= high` by clipping and **count how many rows needed clipping**.
Save out-of-fold predictions for all engines and cycles to `data/processed/oof_predictions.parquet` (CSV fallback) with columns `unit, cycle, true_rul, point, low, high, fold, clipped`.

### 2.4 Benchmark evaluation (comparable to literature)
Train one model on all training engines minus a calibration subset; predict the **last cycle** of each official test engine; report RMSE and the NASA asymmetric score vs `RUL_FD001.txt`.

### 2.5 Metrics written to `reports/model_metrics.json`
- OOF RMSE overall and by true-RUL band (`0-20, 20-40, 40-70, 70+`).
- At `eval_checkpoints_true_rul` (one snapshot per engine per checkpoint so each engine counts equally): **two-sided coverage** of `[low, high]`, **one-sided coverage** `P(true >= low)` (the planner uses `low`), **mean and median width**, mean signed error.
- Fraction of rows clipped for quantile ordering.
- Benchmark RMSE and score.
- Notes string: "ranges are calibrated by predicted-RUL-bin residual percentiles; cycles within an engine are correlated; coverage computed at engine-level checkpoints."

### 2.6 Rule-based fallback (`fallback.py`)
Health-index linear extrapolation producing the same `Estimate` shape with `source="rule_fallback"`. UI must show a visible banner when fallback is active, and `model_metrics` claims must be hidden. Use only for demo continuity.

**Done when:** OOF file exists; causality test passes; metrics JSON complete; low-bound coverage is reported even if poor (do not tune to hit a target; report what you get).

## Phase 3: Health model (replay-driven)

On the training split fit a ridge regression mapping selected sensors to normalised life fraction `cycle / max_cycle`. For a tail at cycle t:
`HI_raw = clip(1 - predicted_life_fraction, 0, 1)`; `HI = EMA(HI_raw, alpha)`; `trend = slope(HI over last trend_window cycles)`.
Output per tail per day: `hi, hi_trend, estimate(low, point, high), estimate_age_days`.

Staleness rule: if a tail's health data is missing for some days, carry the last estimate forward and **decrement by cycles that should have elapsed** (`est_today = last_est - cycles_since_update`, per low/point/high), and set `age_days`.

**Done when:** HI is mostly decreasing on held-out engines (report Spearman correlation of HI vs cycle in the metrics file), staleness carry-forward is unit-tested.

## Phase 4: Scenario generator and strata

`Scenario` contains: `scenario_id`, `stratum`, `seed`, `config_hash`, tails (id, engine unit, part number, initial cycle, `truth.failure_cycle`), spares (unit id, part number, `believed_available_day`, `actual_available_day`, `announce_day`), agencies (bays/day, techs/day, transit days, closed days; believed vs actual), tech records per tail (open defects, cycles since overhaul), data degradation spec (missing-part-number probability, health-feed gap windows, stale record ages), estimate bias in cycles, horizon.

Tail selection: sample `n_tails` distinct engines; `initial_true_rul` drawn uniformly in `[min, max]`; `initial_cycle = failure_cycle - initial_true_rul` (must leave `min_history_cycles` of history). Part numbers alternate A/B with seeded shuffle. Everything derived from `(stratum, seed, config_hash)`.

### Strata (reported separately, never pooled)

| Stratum | Resources and conditions |
|---|---|
| `unconstrained` | spares for every tail, all available day 0; 2 agencies, 2 bays and 6 techs/day each, no closures |
| `spare_constrained` | 4 spares: available days 0, U[0,6], U[8,18], U[15,30]; bays and techs plentiful |
| `tech_constrained` | spares plentiful; 2 bays per agency but techs/day = 2 per agency (one job at a time each); one agency closed on seeded days |
| `data_degraded` | moderate resources (5 spares, 2 bays, 4 techs/day); 35% chance per tail its part number is unusable after ingestion; 50% chance of a 3-6 day health-feed gap; stale tech records |
| `adverse_bias_high` | moderate resources; all estimates shifted **+12 cycles** (model optimistic: dangerous direction) |
| `adverse_bias_low` | moderate resources; estimates shifted **-12 cycles** (model pessimistic) |
| `adverse_late_spare` | as `spare_constrained`, but actual availability of delayed units is 7 days later than believed; truth is revealed when a job fails to start (see §7) |

**Evaluation path vs demo path for degraded data:** in the evaluation path (no CSVs, no ingestion) the generator resolves the degradation spec directly into per-tail `planning_hold` flags, health-feed gap windows and stale-record markers; in the demo path the same effects arise from ingesting the messy CSVs. The consistency test covers clean scenarios only.

Moderate resources means resources constrained enough that contention happens in some seeds, but not always. Check this by inspecting results; adjust numbers in config only, and log in DECISIONS.md.

### Messy CSV pack (`scenario/messy.py`, demo path only)
Writes four CSVs from a Scenario: `health_stream.csv`, `tech_records.csv`, `spares.csv`, `agencies.csv`. Seeded corruption for tech records and spares: tail id formats (`TAIL-01`, `tail 01`, `T01`), part number variants (`PN-ENG-A`, `pn eng a`, `PNENGA`), mixed date formats, missing dates, duplicate rows (some superseding, some conflicting at the same timestamp), negative cycle counts, unknown part numbers, future-dated records. A `clean=True` flag disables corruption (used by the consistency test).

**Done when:** generating the same (stratum, seed) twice gives identical JSON; every stratum generates for all dev seeds without error; tests check stratum properties (e.g., spare_constrained really has fewer immediately available spares than tails).

## Phase 6: Planner (the core; most detail here)

Pure function: `plan_snapshot(state: PlanningState, jobs_spec, ordering="deadline_tail") -> Plan`. No I/O, no randomness, no global state.

### 6.1 Inputs (`PlanningState`)
`today`, `horizon_end`, tails (status, part number, planning RUL in cycles or None, `planning_hold`, open defects), spares (believed available day, part number, assigned/not), agencies (bays/day, techs/day arrays over days, believed closures, transit days), committed placements (jobs already started: they consume calendar capacity and spares and are never moved), config.

### 6.2 Jobs
A job exists for a tail iff the policy requests one (policies, §7). Job fields: `job_id` (`J-<tail>`), tail, part number, `duration = planned_duration + defects * defect_extra` (+ `unplanned_extra_days` if the tail has already failed), `techs_required`, `mode` in {`JIT`, `ASAP`}, `earliest_day = today` (or `today + manual_resolution_delay` for held tails after failure), `deadline_day` (from §3.5; for ASAP jobs `deadline_day = earliest_day`).

### 6.3 Calendars
Per agency, arrays `bays_free[d]` and `techs_free[d]` for `d` in `[today, horizon_end + max_overrun]`, minus closures and minus committed placements. A placement at start `s` at agency `a` with transit `T` and duration `D`:
- tail unavailable on days `[s, s+T+D-1]`;
- bays and techs consumed on work days `[s+T, s+T+D-1]` (each day needs `bays_free >= 1` and `techs_free >= techs_required`, and the agency must not be closed);
- spare needed: compatible part number, `available_day <= s+T`, not already assigned.

Spare choice is best-fit: among eligible units choose the one with the **latest** `available_day <= s+T`, ties by `unit_id`.

### 6.4 Feasibility check and reason codes
`check_start(job, agency, s)` returns the **first failing constraint** in this fixed order: `NO_SPARE`, `NO_SLOT`, `NO_TECH`, or `OK`.

Job-level `binding_constraint`:
- `DATA_HOLD` if the tail has `planning_hold` and the job is not post-failure-resolved;
- `DEADLINE` if `deadline_day < earliest_day`;
- else the result of `check_start` at `s = deadline_day` on the agency candidate that gives the best placement (`NONE` if `OK` at the deadline).
Also store `blocked_by_counts` (how many candidate start days were blocked by each constraint) for diagnostics.

### 6.5 Placement algorithm

```
order jobs by ordering function (default: (deadline_day, tail_id))
for job in ordered jobs:
    if tail has planning_hold and not manual-resolved: status DATA_HOLD, skip placement
    candidates = []
    for agency in agencies (fixed order):
        if mode == JIT:   scan s from min(deadline_day, horizon_end) DOWN to earliest_day
        if mode == ASAP:  scan s from earliest_day UP to horizon_end + max_overrun
        first s where check_start == OK -> candidates.append((s, agency))
    if candidates exist and (mode == ASAP or best s <= deadline_day):
        pick best: JIT -> latest s; ASAP -> earliest s; ties -> lower agency index
        status = ON_TIME; displacement_days = deadline_day - s (JIT)
        reserve spare + calendar capacity
    else:
        # fallback: earliest feasible start after the deadline
        scan s from max(deadline_day + 1, earliest_day) UP to horizon_end + max_overrun across agencies
        if found: status = LATE; days_late = s - deadline_day; reserve
        else:     status = UNSCHEDULED, message "no feasible plan found by this scheduler within the window"
```
`UNSCHEDULED` must never be described as "infeasible" anywhere.

### 6.6 Orderings (`orderings.py`), all deterministic
`deadline_tail` (primary), `deadline_tail_desc` (deadline asc, tail id desc), `longest_first` (duration desc, deadline asc, tail id), `least_slack_first` (deadline - earliest asc, then tail id).

### 6.7 Plan output
`Plan`: placements list, per-job status/start/end/agency/spare/binding/displacement, summary (`late_jobs`, `unscheduled_jobs`, `total_days_late`, `jobs_total`), and `inputs_hash` (sha256 of canonical JSON of the state, ordering, and config hash).

### 6.8 Tests (property and unit)
- No agency exceeds bays or techs on any day; closures respected.
- Each placement uses a compatible, available, uniquely assigned spare.
- Determinism: same state -> identical plan hash; shuffling the input list order of tails/spares does not change the plan.
- ON_TIME placements have `start <= deadline`; LATE have `start > deadline`.
- Hand-built micro-scenarios with known answers: one-bay contention (two jobs, expected order and reason `NO_SLOT`), one-spare contention (`NO_SPARE`), tech shortage (`NO_TECH`), deadline already past (`DEADLINE`), held tail (`DATA_HOLD`).
- `latest_start_offset` table tests (RUL 0, 1, 2, 10; cpd 1 and 2).
- Ordering variants can produce different plans on a contention micro-scenario.

**Done when:** all tests pass and `make e2e` can call the planner on a demo scenario and print placements with reason codes.

## Phase 7: Policies and simulator

### 7.1 Policies (identical resources and rules; they differ only in which jobs they request and the RUL they plan against)

| Policy | Job request rule | Planning RUL | Mode |
|---|---|---|---|
| `reactive` | only for tails that have already failed | n/a | ASAP |
| `reactive_late_warning` | tail failed, or point estimate ≤ `reactive_late_warning_cycles` | point | ASAP |
| `point` | tail whose deadline falls within the horizon | `point` | JIT |
| `range` | same | `low` (chosen conservative policy) | JIT |
| `point_margin` | same | `max(0, point - m)` | JIT |

`m` for `point_margin` is tuned **per stratum on tuning seeds only**: search integer `m` in `margin_grid`, choose the `m` minimising `|mean_unused_life(point_margin, m) - mean_unused_life(range)|`; ties choose smaller `m`. Record `m` per stratum in results. The purpose of this control: show whether the range policy beats a point policy that simply maintains earlier by a matched amount.

Held tails (DATA_HOLD) are handled reactively by every policy: job requested at failure with `earliest_day = failure_day + manual_resolution_delay_days`.

### 7.2 Simulator daily loop (`sim/engine.py`), exact order of operations for day `d`
1. **Completions:** jobs with `end_day == d-1` finish; the tail becomes OPERATING with a fresh engine (no further failure within the horizon).
2. **Information:** apply data gaps; compute each tail's estimate (model estimate + scenario bias, with staleness carry-forward).
3. **Replan:** build `PlanningState` (committed placements fixed; unstarted jobs dropped and re-planned from scratch), ask the policy for jobs, call `plan_snapshot`.
4. **Starts:** every placement with `start_day == d` begins, **if** the believed spare is actually available per `truth`. If not, the job does not start, the spare's believed availability is corrected to the actual date (truth revealed), and the job is re-planned the next day. Record a `START_BLOCKED` event.
5. **Daily status accounting:**
   - tail in an active job: `PLANNED_MAINT` if the job started before failure, else `AOG` (unplanned repair);
   - tail failed and not in a job: `AOG`;
   - otherwise `OPERATING`, and it flies `cycles_per_day` cycles. If cumulative cycles reach `failure_cycle`, status becomes failed from the **next** day (this day still counts OPERATING).
6. Log events (failure, plan created, start, completion, blocked start).

### 7.3 Metrics per run (`sim/metrics.py`)
- `availability = operating_tail_days / (n_tails * H)`.
- `aog_days` (failed waiting + unplanned repair), `planned_maint_days`; invariant: operating + planned + aog = `n_tails * H`.
- `unplanned_failures`, `planned_actions`.
- `unused_life_cycles` = sum over planned removals of true RUL at removal (computed by the simulator from truth; planners never see it).
- `start_blocked_events`.

### 7.4 Tests
- Day-accounting invariant for random scenarios.
- A failure never occurs during maintenance.
- `reactive` never starts a job before a failure.
- Same (scenario, policy) twice -> identical event log.
- Hand-built scenario with one tail and ample resources: `range` policy removes it before failure; `reactive` incurs AOG days equal to the hand-computed value.
- Late-spare scenario produces a `START_BLOCKED` event then recovers.

**Done when:** `make e2e` runs all five policies on one scenario per stratum and prints a metrics table; invariants hold on 100 dev seeds.

## Phase 8: Boundary sweep, classification, counterfactuals

### 8.1 Sweep (`analysis/sweep.py`)
Input: a `PlanningState` snapshot, a policy, and a focal tail. Replace the focal tail's **planning RUL** with each value `r` in `rul_grid` (others fixed), run `plan_snapshot`. For each `r` record: `decision_class` of the focal job in {`NO_JOB_NEEDED, ON_TIME, LATE, UNSCHEDULED, DATA_HOLD`}, `start_day`, `deadline_day`, `binding`, `fleet_late_jobs`.

Boundaries are **discovered**: every adjacent grid pair where `decision_class` changes. There can be zero, one, or several; the sweep need not be monotone and must not assume so. `NO_JOB_NEEDED -> ON_TIME` transitions are tagged `HORIZON_EDGE` (hidden by default in UI). Separately record `KNOCK_ON` boundaries where `fleet_late_jobs` changes while the focal class does not.

Also return the focal tail's current estimate markers (`low`, `point`, `high`) and flag whether `[low, high]` **straddles** a boundary.

### 8.2 Classification (`analysis/classify.py`) for each ON_TIME -> LATE/UNSCHEDULED boundary at the late-side value `r_lo`
1. `binding = ` focal job's binding code at `r_lo`.
2. If `binding == DEADLINE` -> `HORIZON_LIMIT` (not enough time even with free resources).
3. Rerun at `r_lo` under every other ordering in `sweep.orderings`. If any ordering makes the focal job `ON_TIME` with identical resources -> `SCHEDULER_ARTEFACT` (list which orderings).
4. Otherwise -> `RESOURCE_DRIVEN` with `binding`. Then run single-resource relaxation tests at `r_lo` (primary ordering): add one compatible spare available today; add one bay at the relevant agency for all days; add `techs_required` techs for all days. Record `resolved_by` (list; empty means "multi-factor, no single relaxation resolves it").

UI wording: `RESOURCE_DRIVEN` -> "resource-limited under every ordering we tried"; `SCHEDULER_ARTEFACT` -> "disappears under a different ordering, so it reflects the scheduling heuristic". Never claim a sole cause.

### 8.3 Counterfactuals (`analysis/counterfactual.py`, `costs.py`)
Interventions (applied to a copy of state/scenario, **one constraint changed at a time**):
- `EXPEDITE_SPARE(unit, new_available_day=today)`; cost = `expedite_per_day_advanced * days_advanced`.
- `ADD_TECH_CAPACITY(agency, +k techs for window)`; cost = `extra_tech_per_tech_day * k * days`.

Selection for the unblock panel: (a) the intervention that targets the focal job's **binding** resource; (b) a **control** that targets a non-binding resource. Report the actual result of both, whether or not the control changes anything. If the focal job's binding is `NONE`, show "no unblock needed" and show only controls.

For each intervention report: description, illustrative cost and the cost items included (expedite fee only) and excluded (downtime cost, part price, opportunity cost); **planner view** before/after (focal status, start day, `fleet_late_jobs`, `total_days_late`); **simulated view** (paired full simulation of the same scenario, only that change; availability and AOG days delta; label "uses synthetic ground truth, not available in real operations"); `changes_outcome` boolean; `boundary_shift_cycles` (rerun the sweep and compare boundary positions).

All wording: "scenario comparison", not "proves cause". Costs always labelled "illustrative".

### 8.4 Tests
- Micro-scenario where the sweep finds a known boundary at a known RUL.
- A scenario with two boundaries is reported with both.
- A constructed ordering-sensitive scenario is classified `SCHEDULER_ARTEFACT`.
- A constructed one-spare scenario is `RESOURCE_DRIVEN` with `resolved_by` containing the spare relaxation.
- Control intervention on a non-binding resource yields `changes_outcome = false` in a constructed case.
- Paired simulation changes only the intervened parameter (diff the two scenarios).

**Done when:** `make e2e` also prints boundaries with classification for one focal tail per stratum.

## 15. Definition of done (whole project)

2. `reports/model_metrics.json` contains RMSE, coverage (two-sided and low-bound), width, clipping fraction, benchmark score.

4. The UI runs offline, shows the persistent banner, and passes the claims-policy test.
5. At least one demo scenario shows: a discovered boundary classified `RESOURCE_DRIVEN`, an intervention that moves it, and a control that changes nothing (if the data produces no such case, the runbook says so rather than forcing it; choose the demo scenario by searching dev seeds, then confirm on a fresh seed).

3. `adverse_bias_low` stratum.

5. Grouped cross-validation: fall back to one split (60/20/20 by engine) and draw fleets only from held-out engines; log it in DECISIONS.md.

## 19. Gate G0: calibrate scenarios before trusting any result

Run after Phase 7 and before Phase 8. On dev seeds only (never report seeds), for each stratum check and write to `docs/DECISIONS.md`:
- In what fraction of seeds does at least one job get a binding constraint other than `NONE`? Constrained strata should show contention in a meaningful share of seeds, and `unconstrained` in almost none.
- Do `reactive`, `point` and `range` produce different plans in a meaningful share of seeds? If they are identical almost everywhere, the scenario parameters are too easy; adjust resource numbers in `config/default.yaml` only.
- Does at least one dev seed produce a boundary worth demoing (a `RESOURCE_DRIVEN` flip)? If none does, loosen or tighten resources rather than altering planner logic.
Tuning uses dev seeds only. Do not adjust parameters after looking at report seeds.
